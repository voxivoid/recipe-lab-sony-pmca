# The 3D LUT: why it can't be used for look emulation (yet)

Investigated whether the A6000's ISP 3D LUT hardware could give more accurate camera-look emulations than the
gamma/matrix pair documented in [PICTURE-PROFILES.md](PICTURE-PROFILES.md). It can't, today: writes to the LUT banks
are rejected by an ARM TrustZone access-control check that `/dev/mem` from Linux (Non-Secure world) cannot pass.
This records what was found so nobody has to re-run the same tests.

Status (2026-11-21, A6000 FW 3.21): **blocked**. The LUT banks, their format, and the firmware functions that write
them are all mapped. The write itself is rejected in hardware, not in software, so there is no setter to patch the
way `rlisp` patches the gamma/matrix setters.

## Hardware (A6000 FW 3.21)

CXD90014 BIONZ X ISP, physical base `0xF3200000`.

| What | ISP offset | Format |
|------|------------|--------|
| 3D LUT enable | `+0x15D40` | 1 × u32, write 1 to enable bank access, 0 to disable |
| Bank 0 | `+0x17000` | 75 × u32 |
| Bank 1 | `+0x17200` | 60 × u32 |
| Bank 2 | `+0x17300` | 60 × u32 |
| Bank 3 | `+0x17400` | 48 × u32 |
| Bank 4 | `+0x17500` | 50 × u32 |
| Bank 5 | `+0x17600` | 40 × u32 |
| Bank 6 | `+0x17700` | 40 × u32 |
| Bank 7 | `+0x17800` | 32 × u32 |

405 entries total (1620 bytes), matching a 1620-byte contiguous source buffer the firmware builds before handing it
to the bank writer (see below) — banks are not contiguous in ISP register space, but the source buffer is, laid out
bank-by-bank in the same order.

## Firmware functions (av-cam, FW 3.21, load base `0x43541000`)

Found by disassembling `av-cam.bin` (loads at PA `0x83541000`; VA = PA − `0x40000000`).

| Role | VA |
|------|-----|
| Caller (loads LUT data pointer, calls selector) | `0x4381d294` |
| Control setter (writes 18 ISP control params, unrelated to the LUT itself) | `0x43b67988` |
| Selector (enable → 8 bank writes → disable) | `0x43b67a68` |
| Bank writer (switches on bank index, `memcpy`s into the matching ISP bank) | `0x43b67918` |
| Enable function (writes `ISP+0x15D40`) | `0x43b678f0` |
| ISP base getter | `0x43acee62` |

The selector is self-contained: enable, eight `memcpy`-style bank writes, disable. The source format is identical to
the hardware format — no transformation, just a plain copy — so if the write path could be reached, filling the
1620-byte buffer would be the entire job.

## Why writes don't stick

- `/dev/mem` writes to the enable register (`+0x15D40`) succeed and read back correctly.
- `/dev/mem` writes to any bank (`+0x17000`–`+0x17880`) are **silently accepted by the bus but never land**: the
  next read shows the pre-write value, with no error from the write syscall itself.
- Ruled out a timing/latch requirement: a tight `mmap`-based write loop (enable → write → read back, no syscalls in
  between) still shows the bank unchanged.
- This is consistent with an ARM TrustZone / bus-master access-control check on the bank address range: the enable
  register is a normal MMIO register (readable/writable from Non-Secure world), but the banks themselves are gated
  to Secure-world bus masters only. The firmware can write them (it runs with Secure access) in a way Linux cannot.

This is a different failure mode from the gamma/matrix case in PICTURE-PROFILES.md, where the hardware accepts the
write but the firmware later overwrites it. Here the hardware itself refuses the write.

## What was tried and failed

- **Direct `/dev/mem` write to a bank**, enable held high throughout: write is accepted at the bus level, read-back
  shows no change. Ruled out non-atomic writes by writing all words of bank 0 and re-reading immediately after.
- **Tight write loop with no syscalls between enable and write**, to rule out the enable taking effect only after
  some delay: same result.
- **Searching DDR for the firmware's 1620-byte source buffer**, to find a place where it might be patchable before
  the `memcpy`: no match found in a 64 MiB scan of the av-cam DDR window for a Standard Creative Style (the profile
  active during the scan). The buffer may only exist transiently, be built from pieces rather than assembled
  contiguously, or belong to a different Creative Style/table than the one scanned.
- **Firmware code injection**, to run a stub from Secure-world context: a stub was written and assembled to call the
  existing selector (`0x43b67a68`) with injected LUT data, meant to be reached by patching the control setter's
  entry point with a branch. Deployment reached the point of writing the LUT data and the stub into a DDR
  zero-padding region (confirmed empty by write/read-back test), but was not completed — repeated camera power-save
  disconnects interrupted the sequence before the branch patch (the step that would actually invoke Secure-world
  code) was written. **Not proven either way**: this approach has not failed, it just hasn't finished running.

## Open issue: firmware code injection

The remaining untested idea is code injection from within firmware DDR, since code the firmware itself calls runs
in Secure world and should not be subject to the same ACL as a Non-Secure `/dev/mem` write. This needs:

1. A DDR region that is genuinely unused at runtime (zero-filled padding in the firmware image, confirmed zero when
   read live, and confirmed a write there sticks) to hold the injected LUT data and stub code.
2. A branch patch at a firmware function's entry point (the control setter, `0x43b67988`, fires on every Creative
   Style change) that jumps to the stub, runs it, then returns to the original function body.
3. The stub itself calling the existing selector (`0x43b67a68`) with a pointer to the injected LUT data — no need
   to reimplement the bank-write logic, since the selector is self-contained and the source format needs no
   transformation.

This was not completed in this session. It needs a camera session where the connection survives the full deploy
(save originals → write LUT data → write stub → write branch patch → check bank values changed → restore branch
patch) without a power-save disconnect in the middle, since a half-applied patch (branch written but stub/data not)
would make the firmware jump into whatever garbage happens to be at the stub address.

**If attempted again:** the camera's power-save kicks in aggressively during a multi-step `adb`/telnet session.
Keep it awake (half-press the shutter periodically) for the whole sequence, or do the deploy in one shot from a
script rather than one `adb shell` call per step.

## Risk if this is ever made to work

Even with the TrustZone gate bypassed, writing arbitrary values to the 3D LUT is **RAM only** like the gamma/matrix
tables — it does not survive a power cycle on its own, and would need the same kind of reapply-on-boot mechanism
`rlisp` already uses for gamma/matrix. Patching a firmware function's entry point is more invasive than the
`/dev/mem` table writes used elsewhere in this app: a mistake there (wrong branch target, wrong restore order) can
hang or crash av-cam rather than just leaving the ISP table unaffected. Any future attempt should keep the
save-originals-first, write-data-before-code, restore-on-every-exit discipline already used here, and should be
tested with real power-offs per the conventions in [PICTURE-PROFILES.md](PICTURE-PROFILES.md) before being treated
as working.
