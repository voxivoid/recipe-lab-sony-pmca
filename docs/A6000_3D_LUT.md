# The 3D LUT: why it can't be used for look emulation (yet)

Investigated whether the A6000's ISP 3D LUT hardware could give more accurate camera-look emulations than the
gamma/matrix pair documented in [PICTURE-PROFILES.md](PICTURE-PROFILES.md). It can't, today: writes to the LUT banks
are rejected by an ARM TrustZone access-control check that `/dev/mem` from Linux (Non-Secure world) cannot pass.
This records what was found so nobody has to re-run the same tests.

Status (2026-11-21, A6000 FW 3.21): **blocked**. The LUT banks, their format, and the firmware functions that write
them are all mapped. The write itself is rejected in hardware, not in software, so there is no setter to patch the
way `rlisp` patches the gamma/matrix setters.

## Hardware (A6000 FW 3.21)

CXD90014 BIONZ X ISP, physical base `0xF3200000`.

| What | ISP offset | Format |
|------|------------|--------|
| 3D LUT enable | `+0x15D40` | 1 × u32, write 1 to enable bank access, 0 to disable |
| Bank 0 | `+0x17000` | 75 × u32 |
| Bank 1 | `+0x17200` | 60 × u32 |
| Bank 2 | `+0x17300` | 60 × u32 |
| Bank 3 | `+0x17400` | 48 × u32 |
| Bank 4 | `+0x17500` | 50 × u32 |
| Bank 5 | `+0x17600` | 40 × u32 |
| Bank 6 | `+0x17700` | 40 × u32 |
| Bank 7 | `+0x17800` | 32 × u32 |

405 entries total (1620 bytes), matching a 1620-byte contiguous source buffer the firmware builds before handing it
to the bank writer (see below) — banks are not contiguous in ISP register space, but the source buffer is, laid out
bank-by-bank in the same order.

## Firmware functions (av-cam, FW 3.21, load base `0x43541000`)

Found by disassembling `av-cam.bin` (loads at PA `0x83541000`; VA = PA − `0x40000000`).

| Role | VA |
|------|-----|
| Caller (loads LUT data pointer, calls selector) | `0x4381d294` |
| Control setter (writes 18 ISP control params, unrelated to the LUT itself) | `0x43b67988` |
| Selector (enable → 8 bank writes → disable) | `0x43b67a68` |
| Bank writer (switches on bank index, `memcpy`s into the matching ISP bank) | `0x43b67918` |
| Enable function (writes `ISP+0x15D40`) | `0x43b678f0` |
| ISP base getter | `0x43acee62` |

The selector is self-contained: enable, eight `memcpy`-style bank writes, disable. The source format is identical to
the hardware format — no transformation, just a plain copy — so if the write path could be reached, filling the
1620-byte buffer would be the entire job.

## Why writes don't stick

- `/dev/mem` writes to the enable register (`+0x15D40`) succeed and read back correctly.
- `/dev/mem` writes to any bank (`+0x17000`–`+0x17880`) are **silently accepted by the bus but never land**: the
  next read shows the pre-write value, with no error from the write syscall itself.
- Ruled out a timing/latch requirement: a tight `mmap`-based write loop (enable → write → read back, no syscalls in
  between) still shows the bank unchanged.
- This is consistent with an ARM TrustZone / bus-master access-control check on the bank address range: the enable
  register is a normal MMIO register (readable/writable from Non-Secure world), but the banks themselves are gated
  to Secure-world bus masters only. The firmware can write them (it runs with Secure access) in a way Linux cannot.

This is a different failure mode from the gamma/matrix case in PICTURE-PROFILES.md, where the hardware accepts the
write but the firmware later overwrites it. Here the hardware itself refuses the write.

## What was tried and failed

- **Direct `/dev/mem` write to a bank**, enable held high throughout: write is accepted at the bus level, read-back
  shows no change. Ruled out non-atomic writes by writing all words of bank 0 and re-reading immediately after.
- **Tight write loop with no syscalls between enable and write**, to rule out the enable taking effect only after
  some delay: same result.
- **Searching DDR for the firmware's 1620-byte source buffer**, to find a place where it might be patchable before
  the `memcpy`: no match found in a 64 MiB scan of the av-cam DDR window for a Standard Creative Style (the profile
  active during the scan). The buffer may only exist transiently, be built from pieces rather than assembled
  contiguously, or belong to a different Creative Style/table than the one scanned.
- **Firmware code injection**, to run a stub from Secure-world context: a stub was written and assembled to call the
  existing selector (`0x43b67a68`) with injected LUT data, meant to be reached by patching the control setter's
  entry point with a branch. Deployment reached the point of writing the LUT data into a DDR region at VA
  `0x43D70000` that had read back as zero, but was not completed — a camera power-save disconnect interrupted the
  sequence before the stub or branch patch were written.
  - **On reconnecting and re-checking before resuming**, that address turned out not to be safe after all: only the
    first 800 of the 1620 bytes the LUT buffer needs (`+0x000`–`+0x31F`) are actually unused. From `+0x320` onward
    the region holds a live, firmware-maintained pointer table — present in a backup taken *before* any write of
    ours, and still mutating on its own (one word changed value between two reads taken minutes apart with no
    write from us in between). The earlier "confirmed zero, safe" check had only sampled a short window near the
    start of the region, not its full required span, and read it once rather than checking it stayed stable over
    time. No lasting harm resulted — firmware owns and keeps refreshing that table regardless of what we put there
    — but the region cannot hold the full 1620-byte payload, and the injection attempt was stopped before the stub
    or branch patch were written. The setter entry point and the stub region are both still in their stock state.
  - **Lesson for next attempt**: a DDR address reading zero once is not enough to call it safe scratch space. Verify
    across the *entire* span the payload needs, and re-read it after some idle time (or after exercising the
    camera's menus/modes) to catch anything that is only transiently zero rather than structurally unused.

## Firmware code injection: tried and blocked by I-cache partitioning

A complete injection was deployed: verified-safe DDR scratch at PA `0x83FA0000` (4KB+ all-zero, write-sticks,
stable across multiple reads), a 50-byte Thumb stub at PA `0x83FA0800` that calls the existing selector then
replays the overwritten setter prologue and jumps back to setter+4, and a `b.w` branch patch (`38 F0 3A B7`) at
the control setter entry point PA `0x83B67988`. All three writes were confirmed in DDR via read-back.

**It didn't work.** The branch was never taken. Root cause: **ARM TrustZone I-cache partitioning**. The I-cache
tags entries with the NS (Non-Secure) bit. The `ICIMVAU` instruction (I-cache invalidate by VA to PoU), which is
what the Linux `cacheflush` syscall uses, only invalidates entries matching the caller's security state. Our flush
runs in Non-Secure Linux userspace → it invalidates Non-Secure I-cache entries → the Secure-world I-cache entry at
VA `0x43B67988` is unaffected → the CPU keeps fetching the original `push {r4-r6, lr}` from its Secure I-cache
line → the branch to our stub is never taken. Tried flushing from multiple cores (blocked: no `taskset` permission)
and flushing large ranges (64KB) to trigger a full `ICIALLUIS` broadcast (still Non-Secure-only). An `iflush` tool
was built and confirmed to work (successfully calls the cacheflush syscall), but the syscall only reaches
Non-Secure entries by design.

The branch patch and stub are still in DDR (inert — the I-cache never sees them). They survive until the next power
cycle wipes all DDR. No crash risk since the firmware never executes the branch.

## Bank register read behavior

Reading the bank registers from Non-Secure yields uniform values: all 75 entries of bank 0 read as the same u32,
all 60 of bank 1 as a different single u32, etc. The inter-bank gap (e.g. `+0x1712C`–`+0x171FF`) reads as zero.
Values change when the Creative Style changes (bank 0: `0x002B4143` → `0x003B4D63` → `0x002F8B6F` across Standard
→ Vivid → Standard). They are stable across rapid successive reads but not across style changes. This suggests
either:

- The bank registers are write-only for individual entries, with a single-value read-back status per bank (common
  in ISP register banks), or
- The LUT entries really are uniform per bank (identity/flat LUT), which would mean the 3D LUT is a simple
  per-bank color offset rather than a full 3D grid transform.

Either way, we cannot determine the actual per-entry contents via reads from Non-Secure, and cannot build a DDR
search pattern for the firmware's source buffer from the read values.

## What could still work

1. **Overwrite the firmware's LUT data buffer in DDR** (data-only, no code patch, no I-cache issue). The caller at
   `0x4381d294` loads the LUT data pointer from `[r5, #0xC4]` where `r5 = [[arg0] + 0x1B4]`. Tracing this pointer
   chain at runtime (via repeated DDR reads to find the object addresses) would reveal the buffer location. Once
   found, overwriting it and triggering a Creative Style change makes the firmware's own Secure-world code path
   write our data to the banks. Needs more reverse engineering of the object model to find the pointer chain's
   runtime values.

2. **Reconfigure TrustZone protection** (TZASC/TZPC) to allow Non-Secure writes to the bank address range. No
   TZ-related strings found in av-cam.bin — the TZ config is set by the bootloader/secure monitor. The TZPC/TZASC
   register base address is unknown on CXD90014. If found, the config registers are almost certainly Secure-only
   (standard ARM practice), making this a dead end without Secure-world access.

3. **Influence LUT values through the settings store** rather than direct ISP writes. If the Creative Style
   parameters (which determine LUT values) are stored in the same settings store Recipe Lab writes to, they could
   be modified through the existing settings API. This is how `rlisp` works for gamma/matrix. Needs investigation
   of which settings IDs, if any, control the 3D LUT input parameters.

## Risk if this is ever made to work

Even with the TrustZone gate bypassed, writing arbitrary values to the 3D LUT is **RAM only** like the gamma/matrix
tables — it does not survive a power cycle on its own, and would need the same kind of reapply-on-boot mechanism
`rlisp` already uses for gamma/matrix. Patching a firmware function's entry point is more invasive than the
`/dev/mem` table writes used elsewhere in this app: a mistake there (wrong branch target, wrong restore order) can
hang or crash av-cam rather than just leaving the ISP table unaffected. Any future attempt should keep the
save-originals-first, write-data-before-code, restore-on-every-exit discipline already used here, and should be
tested with real power-offs per the conventions in [PICTURE-PROFILES.md](PICTURE-PROFILES.md) before being treated
as working.
